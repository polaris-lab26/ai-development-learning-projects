Week 2: Comparing AI-Generated Contact Form Applications

1. Objective

The aim of this exercise was to compare the contact form applications generated by Gemini and Claude and see how well they met the course requirements.

I looked at whether the applications worked as expected, checked the validation and error messages, and tested how they handled invalid input. I also checked whether the form kept the information I had entered when an error occurred.

The requirements were to use Flask and the Python standard library only, validate information on the server, keep entered values when validation failed, return HTTP 400 for invalid submissions, display a confirmation page after a successful submission, and not store or send messages.

2. Gemini: Implementation and Test Results

Gemini generated three files: app.py, templates/contact.html, and templates/success.html. I ran the application locally using Flask and carried out the following tests.

Gemini’s application worked as expected in all six tests. I was able to check the form’s error messages, confirm that the information entered was retained after validation failed, and verify that an invalid direct request received the required HTTP 400 response.

I also tested script-like input. The response showed that this particular input was escaped. This was a useful security check, although it does not prove that the application is protected against every possible security problem.

The confirmation page showed that the application responded correctly to the submission. No email was sent and no message was stored, as required by the exercise.



3. Claude: Implementation and Test Results

Claude also generated a Flask contact form with separate Python and HTML template files. When I inspected the code, I found checks for required fields and email format, a response intended to return HTTP 400 when validation failed, and a confirmation page for successful submissions.

When I tested the application, submitting a blank form triggered a browser validation message. However, when I subsequently submitted the form, an error appeared:

TemplateNotFound: confirmation.html

This error prevented me from proceeding with the remaining tests, as the application could not display the expected confirmation page.



4. Comparison and Evaluation

Based on my testing, Gemini’s application gave the better results. All six tests I carried out passed, including the direct server-side validation test and the test involving script-like input.

Claude’s code appeared to include the required features, but the template error interrupted the testing process and prevented me from confirming that its successful-submission process worked correctly.

This exercise showed me that looking at code is not enough to know whether an application will work. Even when the expected features appear to be present, the application needs to be run and tested.

Unlike Gemini’s application, which passed all six tests I carried out, Claude’s application encountered an error that interrupted the testing process. A complete comparison based on the results of every test was therefore not possible.



5. Conclusion

The main findings from my testing were:

-   Gemini: All six tests passed, and the application behaved as expected in the scenarios I tested.
-   Claude: The error TemplateNotFound: confirmation.html prevented me from proceeding with the remaining tests.
-   Testing matters: Code that looks correct does not necessarily work when the application is run.
-   My overall finding: Gemini performed better in the tests I completed.
